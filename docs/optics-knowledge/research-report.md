## 3. Подтверждённые знания

1. **Толщина не определяется одним SPH и индексом.** Нужны размер/форма оправы, DBL, децентрация относительно PD, дизайн линзы, иногда min edge и blank diameter.
2. **Фото оправы** даёт только предварительную классификацию (full/semi/rimless, крупность). Не основание для гарантии мм.
3. **Прогрессивы** требуют fitting height и PD (часто монокулярно); IFU производителя задаёт обязательные условия выдачи — онлайн = estimate-only до замеров.
4. **Высокий индекс** оправдан ростом оптической силы и/или крупной/безободковой оправой; при низкой коррекции косметический выигрыш часто мал.
5. **Abbe** обычно падает с ростом индекса: возможен компромисс «тоньше, но больше хроматики» (поликарбонат и ряд high-index).
6. **Фотохром за лобовым стеклом** типично слабее, чем на открытом UV; нельзя обещать уличное затемнение в салоне авто без оговорки / специальной серии.
7. **Blue-light filters:** systematic review (Cochrane) — неопределённая/неподтверждённая польза для eye strain, macular protection, sleep как основание для медицинских обещаний. Допустима опция субъективного комфорта без слова «защита/лечение».
8. **Продажи:** клиенту — исходы (вид, блики, сценарии), мастеру — индекс/SKU; три опции с явной разницей; апселл только при заметной пользе.
9. **Авито-поток** устойчив как: чат → фото рецепта → (фото оправы) → ссылка/3 варианта → визит или заказ после замеров.
10. Каталог проекта содержит **цены и признаки SKU**, но не полный оптический паспорт заготовки.

## 4. Найденные противоречия

| Тема | Сторона A | Сторона B | Как жить в продукте |
|------|-----------|-----------|---------------------|
| Blue light | Маркетинг линз / часть UI («для компьютера», «мягче для экранов» как сильный апселл) | Cochrane: uncertain / no clear clinical benefit for disease & short-term strain | Убрать «защиту»; смягчить до опции комфорта |
| Компьютерные линзы | Клиент ждёт «PC lens» как тип | Для молодых часто SV+AR; office — при пресбиопии/средней дистанции | Не равнять blue-filter = office = «компьютер» |
| Фотохром в авто | Запрос «хамелеон для машины» | Физика лобового / серии drive | Всегда оговорка; не автоапселл обычного фотохрома как drive |
| Индекс | «Чем выше, тем лучше» | Диспенсинг: индекс по силе и оправе | Анти-overkill правила; продавать вид, не число |
| Прогрессив по возрасту | Возраст ≥45 как сигнал | Без ADD/жалоб прогрессив не показан автоматически | Warning ≠ авто-рекомендация progressive во все слоты |
| Rodenstock в прайсе | Имя бренда в каталоге | Возможный white label | Нейминг для клиента — решение владельца |
| Abbe у дистрибьюторов | Заявленные цифры на сайтах поставщиков | Manufacturer / справочники | Не кодировать Abbe из дистрибьютора без сверки |
| Цена «пары» | Прайс за 1 линзу ×2 | Клиент слышит «цену очков» | Явно: линзы + работа; вилка до замера |

## 5. Неподтверждённое

1. Точные мм min edge thickness для всех материалов в практике именно этого салона.
2. Фактическая наценка и «любимые» SKU владельца (в коде есть эвристика «популярный Shamir» — не валидирована владельцем).
3. Реальные сроки склада по каждой позиции.
4. Полная карта соответствия white-label Rodenstock → что говорить клиенту.
5. Клиническая польза конкретных брендовых «accommodation support» / «computer» маркетинговых линий — сверх общего рецепта и геометрии.
6. Числовые пороги age/SPH в `rules.ts` как «истина» — это инженерные эвристики MVP, не утверждённый протокол салона.
7. Abbe по каждой SKU в прайсе (поля нет).
8. Универсальный расчёт толщины без трассировки оправы.

## 6. Недостающие поля в прайсах / нормализованной базе

Сейчас в SKU есть: supplier, name, type, index, coating, цены, SPH/CYL/ADD диапазоны, diameter (грубо), material, флаги photochromic/blueFilter/polarized/aspheric/kids/drive/office и эвристики thinness/comfort/clarity.

**Часто отсутствует или непригодно для гарантий:**

| Поле | Зачем |
|------|-------|
| Abbe number | Честный разговор о качестве картинки vs тонкость |
| Blank diameter options (точный список) | Под крупные оправы / децентрацию |
| Min edge thickness / drillability | Rimless / nylor |
| Base curve options | Wrap / спорт |
| Corridor / fitting range (PAL) | Прогрессивы |
| UV / photochromic activation notes | Авто / улица |
| Lead time / stock vs Rx | Сроки на Авито |
| Warranty / coating brand mapping | Сравнение 3 опций |
| Официальное consumer-facing имя vs white label | Нейминг |
| Точные cyl/sph envelopes для всех Rodenstock | Сейчас частично типовые |

Без этих полей движок может **скорить ассортимент**, но не должен обещать физический результат в мм.

## 8. Правила, которые безопасно внедрять

(После фазы research — в код; **в этой фазе не внедрялись**.)

1. Два слоя языка: клиент без жаргона; мастер — с индексом/SKU.
2. Запрет гарантий толщины/финальной цены без параметров оправы.
3. Обязательная оговорка: фотохром + автомобиль.
4. Запрет медицинских обещаний blue-light / «защита от компьютера».
5. Не назначать progressive единственным/принудительным выбором только по возрасту; при ADD — предупреждение обсудить семейство линз.
6. Штраф / не выбирать high-index overkill при низкой \|SPH\| без запроса максимальной тонкости и учёта оправы.
7. Rimless → эскалация B/C; не финализировать сверление онлайн.
8. Три опции с разной ценностью, не три ценника одного SKU.
9. Бюджет учитывать до показа заведомо недоступного премиума как «единственно правильного».
10. Явная пометка «ориентир» на всех онлайн-ценах.
11. CTA к визиту при progressive / rimless / нет рецепта / меджалобы.
12. Источники правды: manufacturer + peer-review > distributor marketing.

До approval — только мягкие warnings и ручная эскалация мастеру.

## 10. Профессионально неверные части ТЕКУЩЕГО приложения

Наблюдения по коду MVP (`advisor/src/engine/rules.ts`, `recommend.ts`, `clientCopy.ts`, мастер вопросов):

1. **Агрессивный прогрессивный уклон:** при `daily/distance/car` и ADD или age≥50 семейство предпочитает `progressive` первым; age≥45 включает `warnProgressive`. Риск: клиент без жалоб и без готовности к PAL видит прогрессив как норму.
2. **Компьютер = blue filter / «лучше для компьютера»:** скоринг усиливает `blueFilter` и клиентские причины «Лучше подходят для компьютера» — смешивает маркетинг фильтра с задачей экрана.
3. **Техножargon в слое мастера ок, но benefits из каталога** могут просачиваться в `clientReasons`, если engine-причин нет — риск сырых формулировок прайса.
4. **Высокий индекс:** есть штрафы overkill 1.74/1.67, но portfolio всё ещё может поднимать «тонкость» и premium через `thinness`/покрытие без явной связи с оправой (оправа в UI слабый сигнал).
5. **Фотохром в авто:** warning есть, но обычный photochromic не hard-reject при purpose=car; клиент может выбрать «хамелеон» без обязательного видимого дисклеймера на карточке.
6. **Толщина:** UI/копирайт оперируют «потоньше / очень тонкие» без frame metrics — создаёт ощущение обещанного результата.
7. **Labor hardcoded** (1000/1500/2000) без подтверждения владельцем — может врать в «вместе от».
8. **Популярность Shamir (+5)** — коммерческая эвристика без данных салона.
9. **Нет различения estimate vs order-ready** в модели рекомендации.
10. **PRODUCT_AUDIT** уже фиксировал: вопросы без сильного рецепта, поздний бюджет, слабый ввод оправы — согласуется с рисками выше.

1. Убрать/запретить «защиту» и клинические обещания blue-light.
